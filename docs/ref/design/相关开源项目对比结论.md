关于相关开源项目对比结论（panda_quantflow / litegraph / panda_factor / comfyui）

## 1. panda_quantflow 和我们的差别在哪里？

先说一个关键事实：**我们的节点系统本来就是照着它抄的**。[base.py](file:///Users/victor/Desktop/coding/localquant/backend/plugins/base.py#L7-L8) 第一行注释就写着「复刻 panda_quantflow 的 BaseWorkNode」——`input_model / output_model / run` 三方法契约、`@work_node` 装饰器，和它的自定义插件规范完全一致。所以在「节点协议」这一层，我们和它没有差别，差别在周边：

| 维度   | panda_quantflow                                              | localquant（现在 → 将要改）                                  |
| ------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 前端   | **只发布编译产物**。仓库里 `src/panda_web/` 只有 `index.html + assets/`（minified bundle），**没有前端源码** | 自研 React + xyflow（源码在手）→ 换成官方 ComfyUI_frontend（Vue，完整开源、持续维护） |
| 存储   | MongoDB **副本集 + keyFile 鉴权**，且必须去网盘/找小助理下载他们打包好的数据库 | SQLite + DuckDB + parquet 缓存，纯本地文件，零外部服务       |
| 数据源 | 内置近五年数据（来源是他们清洗的 Tushare/RiceQuant/迅投…），随他们的库表结构走 | QMT 实时/历史真数据（零模拟数据原则）                        |
| 架构   | 微服务多进程：要先起 panda_factor 全家桶（6 个包）再起 quantflow server，面向多用户/分布式/企业部署 | 单 FastAPI 进程，本地单人投研工作站                          |
| 许可证 | GPLv3                                                        | MIT → 按 spec 也要转 GPL-3.0（这点上不再是障碍）             |

将要改的方向（ComfyUI 协议适配）和它没有任何交集——它的前端↔后端走的是自己的私有协议，前端还没源码，不可能对着它适配。

## 2. panda_factor 的因子和我们的差别？技术栈一致吗？

同样，**算子语义层我们就是抄它的**：[factor_operators.py](file:///Users/victor/Desktop/coding/localquant/backend/services/factor_operators.py#L1-L10) 注释写明「复刻 PandaAI 公式版量化算子，对齐官网手册」，`RANK/DELAY/STDDEV/CORRELATION/IF/SCALE...` 全套函数名和它一致，公式模式「取最后一行作为因子值」的约定也一致。

真正的差别在**数据结构和数据层**：

- **数据结构**：panda_factor 的 `Factor.calculate()` 要求返回 `['symbol','date']` 多级索引的 Series（长表）；我们是**面板 DataFrame**（index=日期，columns=股票代码），截面算子按行、时序算子按列。语义等价，但代码不能直接互相拷贝，需要 stack/unstack 转换。
- **数据层**：它依赖 MongoDB + `panda_data.init()` + 每晚 8 点 data_hub 自动更新 + 因子持久化到 Mongo；我们是 QMT → parquet/DuckDB。
- **技术栈**：计算核心两边一致（Python + pandas + numpy + FastAPI + pydantic），**基础设施完全不一致**（Mongo vs SQLite/DuckDB）。

所以 AI 没有"写着写着忘了参考项目"——算子层它抄全了，只是把数据结构从长表改成了面板、把 Mongo 换成了本地文件。这两处是有意的取舍，不是遗忘。

## 3. 既然人家开源了，为什么不直接搞下来用？

三个硬性原因，按重要程度排：

1. **它最值钱的部分没真开源。** 工作流画布前端只给了编译后的 dist（我刚核实过 `src/panda_web/` 目录），你拿到的是一个改不动的黑盒 bundle——改个主题色、加个 QMT 节点面板、嵌进你的外壳都做不到。这恰恰是你前端"绕了一大圈"的痛点，而 ComfyUI_frontend 是全源码开放 + Comfy-Org 团队高频维护的，这就是 spec 选 ComfyUI 而不是 panda 前端的根本理由。
2. **数据层被它的私有数据库绑死。** 部署前提是"联系小助理从网盘下载最新数据库"，Mongo 库表结构、数据清洗口径都在他们手里，表结构一更新你就得重新去网盘拉。这和你的"QMT 真数据、零模拟数据、纯本地"原则直接冲突。
3. **体量错配。** 它是面向多用户/企业的微服务架构（Mongo 副本集 + factor 服务 + quantflow 服务 + 调度 + 交易执行），你要的是单机单人投研工作站。搬过来等于养一套用不上的运维负担。

而**能直接拿的部分其实早就拿了**：节点契约（BaseWorkNode/@work_node）和因子算子全集（对齐它官网手册）都已经在我们代码里。剩下没拿的，要么拿不到（前端源码），要么不该拿（Mongo 数据层）。所以现在的路线——协议/算子沿用 panda 的设计、编辑器换成真开源的 ComfyUI、数据层保持 QMT 本地——不是"乱七八糟自己做"，而是把两个上游各自能用的部分拼在了各自最合适的位置。

## 1. 它的成品前端是 ComfyUI 吗？

**长得像，但不是。** 我下载了它 `panda_web/assets/` 里的 `Quantflow-*.js`（工作流页面的代码块）做了字符串统计：

- `litegraph` 出现 11 次、`LGraph` 5 次；
- `Comfy` / `comfy` **0 次**；ComfyUI 协议的特征字段 `object_info`、`class_type`、`prompt_id`、`widgets_values` **全部 0 次**。

结论：它是一个**自研 Vue 应用**（产物里能看到 Vite 打包的 `ChartsView`/`Header`/`Quantflow` 分块 + 一整套 Monaco 编辑器），画布用的是 **litegraph.js 这个库**——而 ComfyUI 旧版画布用的正是同一个库，所以你看到的"那个样子"（深色网格、圆角节点、彩色连线）其实是 litegraph 的样子，不是 ComfyUI 的。

**它做了转换，但不是转成 ComfyUI 节点。** 从压缩代码里能直接看到它的工作流 JSON 结构：

```
{ name, description, litegraph: <画布序列化>, nodes: [...], links: [...] }
```

links 里带 `uuid / previous_node_uuid / next_node_uuid / output_field_name`——注意 `output_field_name`，和我们 runner 里用的字段一模一样（毕竟我们后端是复刻它的）。也就是说它是「litegraph 画布 ↔ 自家 pydantic 节点」的**按字段名**转换，走自己的私有协议；而 ComfyUI 是按**输出索引**连线（spec B.2 里标的那个最易错点）。两者路线完全不同。

**版本**：既然不是 ComfyUI，就不存在"ComfyUI 版本"一说；它内嵌的 litegraph 具体版本埋在 8MB 的压缩 main bundle 里读不出来，但可以确定是**旧式 Canvas 渲染**那一代——视觉上等价于 ComfyUI Nodes 2.0 之前的样子。

## 2. 为什么 ComfyUI 以前五颜六色，现在单一颜色？

两代渲染系统的区别：

- **旧版（LiteGraph Canvas）**：节点标题栏可以有颜色——右键 → Colors 手动上色、很多自定义节点包自带配色、连线按数据类型着色，所以整体花花绿绿。panda_quantflow 也是这个路数（它后端节点有 `box_color` 字段按分组上色，我们 [base.py](file:///Users/victor/Desktop/coding/localquant/backend/plugins/base.py#L15) 里的 `__work_node_box_color__` 就是抄的这个）。
- **Nodes 2.0（Vue 渲染）**：Comfy-Org 换了统一设计系统，默认所有节点都是中性单色卡片，颜色降级为端口类型色和细节强调；且过渡期内旧的节点自定义外观 API（包括第三方改色扩展）**尚未完全兼容**——官方文档明确列了"一些自定义节点可能需要更新才能完全支持"，改色类扩展作者自己都标注"Nodes 2.0 未测试"。

所以不是审美突变，是渲染引擎从 Canvas 换成了 Vue 组件，旧的上色机制还没全接回来。设置里关掉 Nodes 2.0 就能切回旧版彩色外观（这也是 spec C.5 里保留的"逃生舱"）。

## 3. panda_factor 更完善吗？能不能直接换掉我们的因子部分？

**分层看，它只在一个层面更完善，而那个层面恰好是我们不能要的。**

| 层面     | panda_factor                                                 | 我们                                                         | 谁强                               |
| -------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ---------------------------------- |
| 算子库   | 官网手册全集                                                 | [factor_operators.py](file:///Users/victor/Desktop/coding/localquant/backend/services/factor_operators.py) 136 个函数，就是按它官网手册全集对齐复刻的 | **打平**（语义同源）               |
| 分析能力 | `analysis/` 里 IC 工作流、因子分析工作流                     | [factor_research.py](file:///Users/victor/Desktop/coding/localquant/backend/services/factor_research.py)：IC（双向衰减、t 检验）、分层+单调性、换手、中性化、因子相关性、多因子合成、因子池、IC 历史 | **大致打平**，我们的覆盖面不落下风 |
| 数据工程 | 多数据源清洗（Tushare/RiceQuant/迅投）、每晚自动更新、因子持久化+增量提取 | QMT → parquet/DuckDB，无自动更新流水线                       | **它强**                           |
| 周边     | 超级图表、panda_llm、因子大赛社区验证                        | 我们自己的综合报告 + AI 模块                                 | 各有各的                           |

它真正比我们"完善"的是**数据工程层**（自动更新、因子持久化、多源清洗）。但这一层从头到脚焊死在 MongoDB 上：`panda_data.init()` 读 `config.yaml` 连 Mongo，库表结构靠他们网盘分发的数据库，因子返回格式是 `['symbol','date']` 长表。直接换过来意味着：

1. 引入 Mongo 副本集 + 他们的私有库表，放弃 QMT + DuckDB 本地栈——架构原则直接破防；
2. 数据结构从面板改回长表，我们所有因子节点、分析报告、工作流引擎全要跟着改——不是"换一个模块"，是连环手术；
3. 我们的因子部分和工作流引擎、综合报告是打通的（因子节点直接在 runner 里跑面板数据），它的 analysis 和 panda_data 深耦合，剥离出来的适配成本≈重写它的数据访问层，"免费的午餐"就没了。

**我的建议**：不整体替换，但可以"对答案"。反正按 spec 我们要转 GPL-3.0，许可证上和它兼容了——值得做的是拿它的算子实现逐个核对我们 136 个函数的边界处理（停牌、涨跌停、排名并列、中性化的行业处理这类细节），发现我们哪个算子处理得糙就单点移植；它的"因子持久化 + 自动增量更新"思路也可以在我们 DuckDB 层照着实现一份。**抄它的正确性，不抄它的基础设施。**

# litegraph vs ComfyUI 的优劣

先明确一个前提：这俩不是同类东西。**litegraph.js 是一个画布库**（相当于 `@xyflow/react` 的角色），**ComfyUI 是一个完整产品**（画布 + 节点系统 + 队列 + 撤销重做 + 子图 + widget 库 + 扩展 API）。panda_quantflow 走的就是"裸 litegraph + 自己包一层 Vue"的路。

| 维度       | 裸 litegraph.js（panda 路线）                                | ComfyUI 前端整体采用（spec 方案 A）                          |
| ---------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 许可证     | 原版 jagenjo/litegraph.js 是 **MIT**，不传染 GPL             | GPL-3.0，全项目要转（spec 已接受）                           |
| 集成方式   | 作为组件直接嵌进自己的 SPA，无 iframe 接缝                   | 独立应用，iframe 隔离，深浅色分界                            |
| 后端改动   | 几乎为零——按字段名连线，现有 `output_field_name` 引擎直接用（panda 已验证可行） | 要写完整协议适配层：`/object_info`、索引连线转换、WS 消息映射 |
| 得到的能力 | **只有画布**。节点系统、撤销重做、队列、子图、widget、快捷键、模板……全要自己造 | 全套现成，且是社区验证过的成熟交互                           |
| 维护状态   | jagenjo 原版**近乎停更**；活跃的 fork 是 @comfyorg/litegraph（GPL-3），而 Comfy 自己正在用 Nodes 2.0 把它淘汰 | Comfy-Org 全职团队高频维护                                   |
| 本质       | 还是自研编辑器，只是把 xyflow 换成 litegraph                 | 放弃自研内核，只做协议对接                                   |

**我的结论**：裸 litegraph 路线对我们是**伪选项**。spec 立项的动机就是"自研编辑器与 ComfyUI 在交互深度上有差距"（子图、撤销重做、队列），换成 litegraph 一样要自己补这些——而且论画布库本身的维护活跃度，我们现在用的 `@xyflow/react` 反而比 jagenjo 的 litegraph 强，等于换了个更差的轮子重走老路。panda_quantflow 的编辑器完成度也就和我们现状一个水平，这恰好是反面证据。所以维持方案 A 不变；如果 P0 PoC 失败，回退方案也应该是**留在现有 xyflow 编辑器**，而不是转投 litegraph。
