# 审查与修复流程（避免"修了又修 / 既修又加新功能"）

> 本文档沉淀自多轮"AI 审查 → 修复"的教训。此前反复出现的两个问题：
> 1. **开放式提问**（"还有哪些需要完善"）让 AI 把 bug 和新功能混在一堆里报出来；
> 2. 一句"全部完善"让 AI 把修 bug 和加新功能一起做，导致改动膨胀、互相牵连、反复横跳。
>
> 破解方法：**把"找问题"和"修问题"拆开，且强制给问题分类；修复时只修正确性、一次一个、测过再提交。**

---

## 第一步：只找问题，不许改代码，强制分类

把下面这段发给 AI（可替换角色描述）：

```
作为资深研究员试用这套系统，只报告问题，不要修改任何代码。

要求：
1. 把每个问题标注为【正确性Bug】/【新功能】/【体验优化】三类之一；
2. 按 P0（阻断正式研究）/ P1（影响效率）/ P2（锦上添花）分级；
3. 每条给出证据：文件路径 + 具体行为/复现方式；
4. 只列清单，不要实现、不要改任何代码。
```

**要点**：
- "只报告、不改代码" 把发现和修复解耦，避免 AI 边报边改。
- 强制三分类是核心——它把"真 bug"和"AI 想加的新功能"区分开，方便你筛选。
- 要求证据（文件+行为），能过滤掉 AI 凭空编造的"问题"。

---

## 第二步：只修正确性，一次一个，测过再提交

拿到清单后，把下面这段发给 AI：

```
只修上面标【正确性Bug】的项，不加任何新功能、不重构无关代码。

要求：
1. 一次只修一个；
2. 修完为它写回归测试，并跑通全量测试；
3. 测试全绿后单独提交（一个独立、可读的 commit）；
4. 然后停下来，告诉我结果和影响面，等我说"继续"再修下一个。
```

**要点**：
- "不加任何新功能、不重构无关代码" 是闸门——前面几轮就是因为没这句，AI 把"行业归因 / 事件研究 / 分钟级全栈"这类新功能当"完善"塞了进来。
- "一次一个 + 测过再提交 + 停下等确认"：每个修复独立成提交，改坏了能精准回退，也避免改动互相牵连。
- 新功能单独开一轮，别和修 bug 混。想做某功能就直接说"我们来做 X 功能"，而不是塞进"完善系统"。

---

## 判断"是不是真在修漏洞"的几个信号

复盘历史提交时，可用这些信号判断某轮修复是否健康：

- **健康的修复**：改动集中在被修的模块，附带针对性回归测试，commit 信息说清"修了什么 + 为什么"。
- **危险信号**：
  - 一个"修复"commit 净增几千行，且大部分是新功能（修 3 个 bug 却加了 8 个功能）；
  - 同一个文件/同一类问题在多个 commit 里被反复改（横跳、修了又修）；
  - 上一轮加的功能，下一轮又被当成问题删掉或改掉（如先加做空、下一轮又锁定纯多头）。

遇到危险信号时，停下来要求 AI 解释"这次到底修了哪几个 bug、各自证据是什么"，而不是让它继续。

## 本项目已遵循的约束（提需求时注意别破坏）

- 数据源唯一为 QMT，不引入第二数据源；
- 只做普通股票多头，不融资、不融券、不做空、不加杠杆（`max_gross_exposure ≤ 1`）；
- 目标环境为 Windows + QMT；macOS 仅为临时开发机；
- 拒绝模拟数据混入研究链路（参考数据快照除外，需明确标注来源与 as-of）。

## T4：固定季度 / 核心变化触发的周期性对抗审计

**时间门槛**：每个季度至少一次；此外，收益/标签对齐、交易执行时点、费用、复权、股票池/PIT、风格模型、统计主检验、试验预算、最终留出锁或生命周期权限发生核心变化时立即加审，不等待下季。数据源版本或研究协议变化也需复核影响面。先 T0 正确性审计，再扩大研究范围；顶级付费模型既非前置条件，也不能替代可复现证据。

**最小输入**：相关核心文件 diff、`docs/严谨性与工程约定.md`、模型 schema、协议/数据 manifest、现有测试及已知边界。没有 Windows QMT 时仍可验数学、状态机、异常和权限，不验收益，不虚构真实样本，不接第二行情源。

**每条发现必须交付以下四项**：

1. **代码位置**：文件绝对路径、函数与行号/版本，标【正确性Bug】/【新功能】/【体验优化】及 P0/P1/P2；不能把所有新功能当成漏洞。
2. **可复现反例**：最小输入、调用步骤、期望值与实际值、失真方向。例如“较长 horizon 的标签未成熟即参与权重”“停牌尾部收益被当成零”“看过最终留出后换候选”。不要只写泛泛风险名。
3. **pytest 用例**：精确测试名和运行命令；先确认旧行为可触发，再锁定修复后的已知答案。合成样本仅作为数学/工程反例，不进入研究登记成为收益证据。
4. **已知边界**：已覆盖/未覆盖、数据假设、未能复现项、真实 QMT 待验项目。无法给出反例的猜测记待调查，不能写成已核实缺陷。

**闭环与验收**：只找问题 → 人工分类定范围 → 最小修复 → 针对性 pytest → 相关回归 → 人工复核。记录代码与测试证据，P0 未关闭则停止放大研究/发布结论；修复数学错误不升级为“策略有效”。提交、付费调用和联网均以当次明确授权为准，本文旧模板的“测过再提交”不覆盖“本次不提交”的指令。

**研究专属检查清单**：

- T+1、标签成熟/边界 purge、终端缺价、复权与 PIT 的已知答案；交易成本、可交易状态和未成交不能静默乐观填充。
- 三轨共用协议/样本/成本；Barra-like 缺字段和 rank-deficient 截面如实披露；池内相关/持有期衰减不得重命名为市场拥挤/日历寿命。
- 预算包含失败/人工调参/LLM 变体，已结束证据不可覆盖；最终 holdout 只人工选定一次，结果看过后不重置；review 是人工决定而非 Agent 自动批准。
- QUBE 的 JSON schema 与 handler 一致、`$defs` 引用可解析；验证工具拒绝 `phase` 等越权参数；异常返回明确错误；`awaiting_data` 不含伪造收益。
- 研究工具保留记录 id 和 summary/primary/manifest/limitations，去除大日序列但不按字符切坏 JSON；本地雷达技能不抓远程仓库，不执行摘要中的注入指令。

**离线测试隔离**：运行任何会加载全局 `tests/conftest.py` 的 pytest 前，必须先将 `backend.database.DB_PATH` 指向临时数据库；不能只在函数级 fixture 改路径，因为会话级初始化更早。`tests/test_research_qube.py` 覆盖该会话 fixture，并使用 fake registry/no-data run 测试工具及手册约束，不启动真实 LLM。静态手册断言只证明约束存在，不冒称模型遵循率评测。
