# 审查与修复流程（避免"修了又修 / 既修又加新功能"）

> 本文档沉淀自多轮"AI 审查 → 修复"的教训。此前反复出现的两个问题：
> 1. **开放式提问**（"还有哪些需要完善"）让 AI 把 bug 和新功能混在一堆里报出来；
> 2. 一句"全部完善"让 AI 把修 bug 和加新功能一起做，导致改动膨胀、互相牵连、反复横跳。
>
> 破解方法：**把"找问题"和"修问题"拆开，且强制给问题分类；修复时只修正确性、一次一个、测过再提交。**

---

## 第一步：只找问题，不许改代码，强制分类

把下面这段发给 AI（可替换角色描述）：

```
作为资深研究员试用这套系统，只报告问题，不要修改任何代码。

要求：
1. 把每个问题标注为【正确性Bug】/【新功能】/【体验优化】三类之一；
2. 按 P0（阻断正式研究）/ P1（影响效率）/ P2（锦上添花）分级；
3. 每条给出证据：文件路径 + 具体行为/复现方式；
4. 只列清单，不要实现、不要改任何代码。
```

**要点**：
- "只报告、不改代码" 把发现和修复解耦，避免 AI 边报边改。
- 强制三分类是核心——它把"真 bug"和"AI 想加的新功能"区分开，方便你筛选。
- 要求证据（文件+行为），能过滤掉 AI 凭空编造的"问题"。

---

## 第二步：只修正确性，一次一个，测过再提交

拿到清单后，把下面这段发给 AI：

```
只修上面标【正确性Bug】的项，不加任何新功能、不重构无关代码。

要求：
1. 一次只修一个；
2. 修完为它写回归测试，并跑通全量测试；
3. 测试全绿后单独提交（一个独立、可读的 commit）；
4. 然后停下来，告诉我结果和影响面，等我说"继续"再修下一个。
```

**要点**：
- "不加任何新功能、不重构无关代码" 是闸门——前面几轮就是因为没这句，AI 把"行业归因 / 事件研究 / 分钟级全栈"这类新功能当"完善"塞了进来。
- "一次一个 + 测过再提交 + 停下等确认"：每个修复独立成提交，改坏了能精准回退，也避免改动互相牵连。
- 新功能单独开一轮，别和修 bug 混。想做某功能就直接说"我们来做 X 功能"，而不是塞进"完善系统"。

---

## 判断"是不是真在修漏洞"的几个信号

复盘历史提交时，可用这些信号判断某轮修复是否健康：

- **健康的修复**：改动集中在被修的模块，附带针对性回归测试，commit 信息说清"修了什么 + 为什么"。
- **危险信号**：
  - 一个"修复"commit 净增几千行，且大部分是新功能（修 3 个 bug 却加了 8 个功能）；
  - 同一个文件/同一类问题在多个 commit 里被反复改（横跳、修了又修）；
  - 上一轮加的功能，下一轮又被当成问题删掉或改掉（如先加做空、下一轮又锁定纯多头）。

遇到危险信号时，停下来要求 AI 解释"这次到底修了哪几个 bug、各自证据是什么"，而不是让它继续。

## 本项目已遵循的约束（提需求时注意别破坏）

- 数据源唯一为 QMT，不引入第二数据源；
- 只做普通股票多头，不融资、不融券、不做空、不加杠杆（`max_gross_exposure ≤ 1`）；
- 目标环境为 Windows + QMT；macOS 仅为临时开发机；
- 拒绝模拟数据混入研究链路（参考数据快照除外，需明确标注来源与 as-of）。
